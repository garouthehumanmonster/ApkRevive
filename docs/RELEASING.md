# Release Process & Distribution Guide

This document outlines the automated release pipeline, cryptographic signing architecture, build provenance verification, and PyPI Trusted Publishing configuration for ApkRevive.

---

## 1. Automated Release Pipeline Overview

Releases are triggered by pushing annotated git tags matching `v*` (e.g. `v0.5.0a1` or `v0.5.0`). The pipeline in `.github/workflows/ci.yml` executes:

1. **Multi-Platform CI**: Unit tests, linting (`ruff`), type-checking (`mypy`), dependency vulnerability auditing (`pip-audit`), and Hypothesis fuzzing across Linux, macOS, and Windows on Python 3.9, 3.12, and 3.13.
2. **Android Companion CI**: Gradle verification, linting, unit tests, and dual APK compilation (debug and release).
3. **Multi-Tier Canary Matrix & SARIF Diagnostics**: Hermetic verification of all 8 canary vectors and generation of SARIF diagnostics.
4. **16KB Page-Size Emulator Verification**: Real boot and execution verification on an Android 15 (API 35) 16KB system image (`scripts/ci_16kb.sh`).
5. **Build Provenance Attestations**: Cryptographic SLSA build provenance attestations generated via `actions/attest-build-provenance` for Python distribution wheels/sdist and Android Companion APKs.
6. **Distribution & Release**:
   - Compiles Python source distribution (`sdist`) and wheels (`bdist_wheel`).
   - Downloads companion APK artifacts and SARIF reports.
   - Publishes to PyPI via OIDC Trusted Publishing (for stable releases only).
   - Generates GitHub Release with assets and attestations, marking pre-releases appropriately.

## 2. PyPI Trusted Publishing (OIDC) Setup

ApkRevive uses PyPI's OpenID Connect (OIDC) Trusted Publishing to publish releases without long-lived API tokens or passwords.

### Pending Publisher Configuration
Because `apkrevive` is not yet registered on PyPI, configure a **Pending Publisher** before the first stable release:

1. Log in to [pypi.org](https://pypi.org/).
2. Navigate to **Account settings** -> **Publishing** -> **Add a pending publisher**.
3. Fill in the publisher details:
   - **PyPI Project Name**: `apkrevive`
   - **Owner**: `garouthehumanmonster` (GitHub organization or user account owning the repository)
   - **Repository name**: `apkrevive`
   - **Workflow name**: `ci.yml`
   - **Environment name**: `pypi`
4. Submit the pending publisher registration.
5. On the GitHub repository (`garouthehumanmonster/apkrevive`):
   - Navigate to **Settings** -> **Environments**.
   - Create an environment named `pypi`.
   - Configure deployment branch protection rules (e.g., restrict deployments to tags matching `v*`).

### Pre-Release vs. Stable Tags
- **PEP 440 Pre-Release Tags** (`^v[0-9]+\.[0-9]+\.[0-9]+(a|b|rc)[0-9]+$`, e.g. `v0.5.0a1`):
  - GitHub Release is automatically flagged with `prerelease: true`.
  - The PyPI publication step is explicitly **skipped** to prevent untracked alpha packages on PyPI.
- **Stable Tags** (`v0.5.0`, `v1.0.0`):
  - GitHub Release is marked as standard stable release.
  - PyPI publication executes via the `pypi` environment using trusted OIDC tokens.

## 3. Verifying Artifact Attestations (SLSA Provenance)

All release artifacts (Python wheels, source archives, and Companion APKs) generated by the release pipeline are cryptographically signed using GitHub's artifact attestation system backed by Sigstore.

To verify the provenance and authenticity of any released artifact:

### Using GitHub CLI (`gh`)
Run `gh attestation verify` specifying the repository owner:

```bash
gh attestation verify <artifact-path> --owner garouthehumanmonster
```

### Verification Examples

- **Verifying a Python wheel distribution**:
  ```bash
  gh attestation verify dist/apkrevive-0.5.0-py3-none-any.whl --owner garouthehumanmonster
  ```

- **Verifying a source distribution tarball**:
  ```bash
  gh attestation verify dist/apkrevive-0.5.0.tar.gz --owner garouthehumanmonster
  ```

- **Verifying the Companion APK**:
  ```bash
  gh attestation verify dist/companion/ApkRevive-Companion-v0.5.0.apk --owner garouthehumanmonster
  ```

### What Verification Asserts
1. The artifact binary was built directly on GitHub Actions infrastructure.
2. The build originated from the authoritative repository (`garouthehumanmonster/apkrevive`).
3. The build was triggered by `.github/workflows/ci.yml` at the exact commit SHA and tag.
4. The artifact has not been modified or tampered with since creation.

## 4. Android Companion App Signing

Companion APKs (`apkrevive-android`) are compiled during CI in the `android-ci` job.

### GitHub Secrets for Production Signing
To sign release APKs with the official distribution key, configure the following 4 repository secrets in **Settings** -> **Secrets and variables** -> **Actions**:

- `ANDROID_KEYSTORE_B64`: Base64-encoded Java Keystore (`.keystore` or `.jks` file).
- `ANDROID_KEYSTORE_PASSWORD`: Access password protecting the keystore file.
- `ANDROID_KEY_ALIAS`: Key alias within the keystore (e.g. `apkrevive`).
- `ANDROID_KEY_PASSWORD`: Access password protecting the private signing key.

### Generating the Keystore
To generate a new release keystore locally:

```bash
keytool -genkeypair -v \
  -keystore release.keystore \
  -alias apkrevive \
  -keyalg RSA \
  -keysize 4096 \
  -validity 10000 \
  -storetype PKCS12
```

Generate the Base64 payload for `ANDROID_KEYSTORE_B64`:
- On Linux/macOS:
  ```bash
  base64 -w 0 release.keystore
  ```
- On Windows (PowerShell):
  ```powershell
  [Convert]::ToBase64String([IO.File]::ReadAllBytes("release.keystore"))
  ```

### Offline Backup Protocol for Release Keystore
The release keystore is the root of trust for Android Companion APK updates. Android enforces signature matching across package updates; losing the release key prevents releasing updates without forcing users to completely uninstall existing installations.

The following offline backup protocol must be observed:

1. **Air-Gapped Media**:
   - Store the original `release.keystore` file on at least two independent, encrypted, air-gapped physical storage devices (e.g., AES-encrypted USB drives or hardware security modules).
   - Store devices in geographically distinct, physically secure locations (e.g. fireproof safes).
2. **Credential Segregation**:
   - Store keystore passwords (`ANDROID_KEYSTORE_PASSWORD`, `ANDROID_KEY_PASSWORD`) in an encrypted password manager (1Password, Bitwarden) with hardware-token MFA.
   - Do **not** store the passwords alongside the physical keystore media.
3. **Strict Zero-Commit Policy**:
   - Keystores must **never** be committed to git repositories or public storage buckets.
   - Repository `.gitignore` rules must enforce exclusions for `*.keystore`, `*.jks`, and `*.p12`.
4. **Disaster Recovery**:
   - If the keystore secret is lost from GitHub repository secrets, restore `ANDROID_KEYSTORE_B64` by re-encoding from one of the physical air-gapped backup media.
   - If the private key is permanently lost or compromised:
     - Rotate keys and release a new APK signed with the replacement keystore.
     - Document the signature break in release notes; existing users must uninstall previous versions (`adb uninstall com.apkrevive`).

### CI Keystore Handling & Fallback
- Keystores are decoded dynamically in memory on the runner (`apkrevive-android/release.keystore`) during the build step and deleted immediately upon job completion.
- If `ANDROID_KEYSTORE_B64` is not configured:
  - The release build falls back to signing with the standard Android debug keystore.
  - The artifact is explicitly named `ApkRevive-Companion-<version>-debug-signed.apk`.
  - A CI warning is emitted (`::warning::Naming release APK with -debug-signed suffix because release keystore was absent`).

> [!WARNING]
> **Signing Key Migration**: Companion APKs for v0.5.0a1+ use a separate keystore from v0.4.0. Upgrading from v0.4.0 requires uninstalling the previous APK (`adb uninstall com.apkrevive`).
