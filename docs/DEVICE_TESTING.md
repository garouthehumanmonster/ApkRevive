# Device Testing & Verification Plan

This document defines the formal device verification matrix and operational test protocol across Android 14, Android 15, and Android 16 (on both physical devices and headless/GUI emulators).

---

## 1. Target SDK Floor & Bypass Compatibility Matrix

Android 14 (API 34) introduced a platform floor on `targetSdkVersion` to prevent malware from targeting obsolete APIs to evade runtime permissions. Android 15 (API 35) and Android 16 (API 36+) enforce this floor strictly.

| **Android 15** | 35 | Vanilla Ice Cream | `targetSdk >= 24` | Direct install of `targetSdk < 24` rejected (`INSTALL_FAILED_DEPRECATED_SDK_VERSION`) | Supported via `--bypass-low-target-sdk-block` (ADB / Shizuku shell / `installFlags |= 0x01000000`) | [UNVERIFIED - Hardware Pending] |
| **Android 16** | 36+ | Baklava | `targetSdk >= 24` *(UNVERIFIED: default platform floor not finalized in public AOSP source)* | Direct install of `targetSdk < 24` rejected (`INSTALL_FAILED_DEPRECATED_SDK_VERSION`) | Supported via `--bypass-low-target-sdk-block` (ADB / Shizuku shell / `installFlags |= 0x01000000`) | [UNVERIFIED - Hardware Pending] |

## 3. Test Execution Protocols

### Method A: Host CLI Verification (via ADB)

Execute the verification steps against an attached device or running emulator:

```bash
# Verify attached target
adb get-serialno
adb shell getprop ro.build.version.sdk

# Build canaries if not already compiled
python canaries/build_canaries.py

# 1. Test Control Canary (targetSdk 24)
adb install -r canaries/build/canary_install_floor_control.apk
# Expected output:
# Performing Streamed Install
# Success

# 2. Test Failing Canary without bypass (targetSdk 22 on API 34+)
adb install -r canaries/build/canary_install_floor_failing.apk
# Expected output:
# Failure [INSTALL_FAILED_DEPRECATED_SDK_VERSION: App package must target at least SDK version 24, but targets 22]

# 3. Test Failing Canary with bypass flag
adb install --bypass-low-target-sdk-block -r canaries/build/canary_install_floor_failing.apk
# Expected output:
# Performing Streamed Install
# Success
```

### Method B: Automated Python Canary Matrix Runner

Run the full dual-assertion matrix runner:

```bash
python -m unittest tests/test_canaries.py
# or against live ADB device:
python scripts/verify_canary_matrix.py
```

### Method C: On-Device Companion App Verification (`apkrevive-android`)

1. **Prerequisites**:
   - Install `apkrevive-android.apk` on the test device.
   - Start the Shizuku service via Wireless Debugging (`shizuku.rikka.app`) or root (`su`).
   - Launch ApkRevive and grant Shizuku binder permissions.

2. **Verification Steps**:
   - **Control Canary**:
     - Tap **Select APK** and choose `canary_install_floor_control.apk`.
     - Confirm Triage Card: **GREEN (Runnable Unmodified)**. Subtitle displays standard installation.
     - Tap **Install App**.
     - Verify status transitions: `Opening Stream` -> `Writing APK` -> `Committing Session` -> `Installation succeeded!`.
   - **Failing Canary**:
     - Tap **Select APK** and choose `canary_install_floor_failing.apk`.
     - Confirm Triage Card: **GREEN (Bypass Required)**. Subtitle displays targetSdk bypass notification.
     - Tap **Install App**.
     - Verification: The app sets `params.installFlags |= 0x01000000`. If the device ROM restricts reflection on `installFlags`, the companion app automatically falls back to `installApkViaShell` (`pm install -S <size> --bypass-low-target-sdk-block`).
     - Verify status notification: `Installation succeeded!`.

## 4. OBB Expansion Delivery Verification (Android 11+)

Android 11+ (API 30+) strictly isolates `/storage/emulated/0/Android/obb/` from normal application storage permissions. Verify OBB delivery via privileged shell:

```bash
# Validate delivery using ApkRevive CLI
apkrevive push-obb \
  --obb canaries/build/main.100.com.apkrevive.canary.obbversion.control.obb \
  --package com.apkrevive.canary.obbversion.control \
  --current-apk-version 150

# Host push via ADB (Shell UID 2000 has access):
adb shell mkdir -p /storage/emulated/0/Android/obb/com.apkrevive.canary.obbversion.control
adb push canaries/build/main.100.com.apkrevive.canary.obbversion.control.obb /storage/emulated/0/Android/obb/com.apkrevive.canary.obbversion.control/

# Verify file presence and permissions
adb shell ls -la /storage/emulated/0/Android/obb/com.apkrevive.canary.obbversion.control/
```

### Multi-User Storage Limitations (Android 11+)
`/storage/emulated/<userId>/Android/obb/` requires storage volumes mounted and accessible to UID 2000 (`com.android.shell`). On secondary users or work profiles (e.g. `userId=10`), SELinux multi-user boundary isolation or locked/unmounted profile storage will block push operations until the profile is unlocked.

### C. Crash & A/B/C Anomaly Investigation

Empirical A/B/C testing on modern Android (API 34+) resolved earlier hypotheses regarding `acr.browser.barebones` and `android.androidVNC`:
- **Crash Buffer Evidence**: The crash buffer (`logcat -d -b crash`) was verified completely clean (0 crashes, 0 fatal exceptions) for both applications.
- **Root Cause of Process Stall**: When installed with `targetSdk < 23` on modern Android, the platform permission controller intercepts app launch with a system modal `ReviewPermissionsActivity` (`com.google.android.permissioncontroller/com.android.permissioncontroller.permission.ui.ReviewPermissionsActivity`). Until the user clicks "Continue" on the dialog, the target process is not spawned (`pidof` returns empty).
- **Target SDK Bump Resolution**: When revived with `--bump-target-sdk 24`, the modern permission model applies. The app launches immediately into active background execution and displays standard runtime permission requests (`GrantPermissionsActivity`) without blocking process creation.
- **Conclusion**: The targetSdk bump does NOT cause crashes; it prevents the legacy permission review dialog deadlock.
